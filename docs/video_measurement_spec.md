# 動画計測の仕様：何を、どの定義で、どれくらいの精度で測るか

このプロジェクトの画面は、ランニング動画から測った値を、すでに作ってある3つのモデルに入れて結果を出します。動画から値を出す部分は、この仕様に合わせてください。

| 画面の表示 | 使うモデル（ファイル） | 入力に必要な値 |
|---|---|---|
| ① 走り方のタイプ | `analysis/step3_types/outputs/types_display.json` | ピッチ、接地の仕方、骨盤の傾き、膝の屈曲 |
| ケガの予測 | `analysis/step5_evidence/outputs/prediction_models.json` | リズム：ピッチ、Duty factor、接地の仕方、左右差／フォーム：骨盤の傾き、股関節の内転、膝の屈曲、膝の外反 |
| ② 部位ごとの負担 | `analysis/step4_load/outputs/load.json` | 下の表の「負担」の列の値 ＋ 速度・身長・体重 |

---

## 1. 撮影の条件

| 項目 | 条件 |
|---|---|
| 走る場所 | トレッドミル（研究データと同じ条件）。速度は **時速10km** を基本にする（9〜13km の範囲なら補正できる） |
| カメラの向き | **真後ろ**（フォームの角度）と **真横**（リズム・側方の角度）の2本。同じ人を同時に撮るのが理想 |
| カメラの位置 | 固定（三脚など）、高さは腰くらい、全身（頭〜つま先）が画面の6〜8割に入る距離 |
| フレームレート | **120fps 以上を推奨**（接地時間の精度のため）。最低 60fps |
| 長さ | 走り始めてから落ち着いた後の **14歩以上**（片脚7歩以上） |
| 服装 | 脚の形が分かる服（短パンなど） |
| 一緒に記録する情報 | 速度（km/h）、身長（cm）、体重（kg）、性別 |

## 2. 出力の形式（1本の撮影ごとに1つの JSON）

```json
{
  "video": {"rear": "xxx_rear.mp4", "side": "xxx_side.mp4", "fps_rear": 120, "fps_side": 120},
  "subject": {"speed_kmh": 10.0, "height_cm": 172, "mass_kg": 64, "sex": "M"},
  "rhythm": {"cadence_spm": 166.2, "contact_s": 0.251, "flight_s": 0.110, "duty": 0.695,
             "foot_strike": "rearfoot", "cadence_asym_pct": 1.8, "duty_asym_pct": 2.5, "alt_strike": false,
             "pelvis_vertical_osc_mm": 88.0},
  "legs": {
    "L": {"CPD": 5.1, "HADD": 80.2, "KA": 2.0, "KF": 39.5,
          "knee_flex_contact": 9.8, "shank_angle_contact": -7.2, "foot_angle_contact": 12.0, "overstride": 0.15,
          "n_steps": 7},
    "R": {"...": "左と同じ項目"}
  },
  "quality": {"step_sd": {"KF": 1.2, "CPD": 0.8, "...": "歩ごとの SD"},
              "low_confidence_frames_pct": 3.5, "notes": []}
}
```

- 値は **歩ごとに計算して、中央値** を出す（外れた歩は除く）。`quality.step_sd` に歩ごとの SD も入れる
- 測れなかった値は `null`（モデル側で参加者の中央値で補う）

## 3. 測る値の定義

座標は画像の2D。**後方** = 後ろから撮った画像、**側方** = 横から撮った画像。
**接地** = 足が地面に着いた最初のコマ、**離地** = 足が離れた最初のコマ、**立脚中期** = 接地と離地の真ん中のコマ。
角度の定義は、研究データ（Loh 2025 の2D動画解析、Fukuchi 2017 のマーカーから計算した値）にそろえてあります。**向き（符号）を必ず合わせてください。**

### リズム（側方）
| 値 | 定義 | 単位 |
|---|---|---|
| `cadence_spm` ピッチ | 60 ÷ 1歩の時間（接地から次の反対側の接地まで） | 歩/分 |
| `contact_s` 接地時間 | 接地から離地まで | 秒 |
| `flight_s` 滞空時間 | 離地から次の反対側の接地まで | 秒 |
| `duty` Duty factor | 接地時間 ÷ 1歩の時間 | 比 |
| `foot_strike` 接地の仕方 | 接地の瞬間に、踵がつま先より先に着いたら `rearfoot`、それ以外は `non_rearfoot` | 分類 |
| `alt_strike` | 左右で `foot_strike` が違う | 真偽 |
| `cadence_asym_pct`、`duty_asym_pct` 左右差 | 左右の1歩の時間（Duty factor）の差 ÷ 平均 × 100 | % |
| `pelvis_vertical_osc_mm` 骨盤の上下動 | 1歩の間の、左右の股関節の点の中点の上下の幅。画面上の長さを、身長で mm に換算 | mm |

### フォーム（後方、立脚中期、立脚している脚について）
| 値 | 定義 | 向き |
|---|---|---|
| `CPD` 骨盤の傾き | 左右の骨盤の点（股関節の点で代用）を結ぶ線の、水平からの角度 | **反対側の骨盤が下がると正** |
| `HADD` 股関節の内転 | 立脚側の股関節の点から反対側の股関節の点への線と、立脚側の太もも（股関節の点→膝の点）のなす角 | **約80°前後。内転が大きい（膝が内側に入る）ほど小さくなる** |
| `KA` 膝の外反 | 股関節・膝・足首の点がなす角の、180°からのずれ | **膝が「股関節と足首を結ぶ線」より外側にあると正** |

### 側方の角度（立脚している脚について）
| 値 | 定義 | 向き |
|---|---|---|
| `KF` 膝の屈曲 | 立脚中期の、太もも（股関節→膝）とすね（膝→足首）の角度の、180°からのずれ | 深く曲がるほど大きい（約40°前後） |
| `knee_flex_contact` 接地時の膝の屈曲 | 接地の瞬間の `KF` と同じ定義 | 約10°前後 |
| `shank_angle_contact` 接地時のすねの傾き | 接地の瞬間の、足首→膝の線の鉛直からの角度 | **膝が足首より進行方向の前にあると正**（通常は負、約−8°） |
| `foot_angle_contact` 接地時の足の角度 | 接地の瞬間の、踵→つま先の線の水平からの角度 | **つま先が上がっていると正**（踵接地で約+14°） |
| `overstride` オーバーストライド | 接地の瞬間の、踵の骨盤の中心からの前方距離 ÷ 脚の長さ（股関節の点〜足首の点） | 比（約0.15） |

**参考の元になっている計算**：`analysis/step4_load/41_marker_features.py`（マーカーから同じ値を計算したコード）

## 4. 精度を上げる優先順位と目標

「優先」は、画面のどれだけ多くの結果に、どれだけ強く効くかで決めました（モデルの係数の大きさと、使われている場所の数から）。
「目標の誤差」は、研究参加者の値のばらつき（SD）と、ステップ4で入力に誤差を足して試した結果から決めた**目安**です。

| 優先 | 値 | 使われる場所 | 参加者のばらつき（SD） | 目標の誤差 | 許容できる誤差 |
|---|---|---|---|---|---|
| **1** | `duty`、`contact_s` | 負担（4部位すべてで上位） | 0.054、0.024秒 | 0.015、**0.010秒** | 0.02、0.015秒 |
| **1** | `cadence_spm` | タイプ、負担 | 9.3歩/分 | 2歩/分 | 3歩/分 |
| **1** | `foot_strike`（`foot_angle_contact`） | タイプ、予測、負担 | 足の角度 6.5° | 分類の一致 90%以上、角度 2° | 分類 85%、角度 3° |
| **1** | `KF` | タイプ、**フォームの予測で最も効く**、負担 | 3.7〜4.5° | 1.5° | 3° |
| **1** | `CPD` | タイプ、予測、負担 | 2.6° | 1° | 2° |
| **2** | `HADD` | 予測で2番目、股関節の負担で最も効く | 2.8〜4.1° | 1.5° | 3° |
| **2** | `pelvis_vertical_osc_mm` | 負担（上位） | 14 mm | 5 mm | 10 mm |
| **2** | `overstride`、`knee_flex_contact` | 膝の負担で最も効く | 0.031、4.3° | 0.015、2° | 0.03、3° |
| 3 | `KA` | 予測（効きは小さい）、負担 | 3.9〜6.3° | 2° | 3° |
| 3 | `shank_angle_contact` | 負担（効きは小さい） | 2.1° | 1° | 3° |
| 3 | 左右差、`alt_strike` | リズムの予測（係数はほぼ0） | — | — | 測れなければ `null` でよい |

**誤差の種類に注意**
- **決まった方向にずれる誤差（系統誤差）**：例えば「いつも3°大きく出る」。タイプの区切り（ピッチ162.6歩/分、骨盤の傾き5.5°、膝の屈曲40.5°）の判定を大きく狂わせます。正解データと比べて平均のずれが分かれば、差し引いて補正できます
- **ばらつく誤差（偶然誤差）**：歩ごとに上下する誤差。歩数を増やして中央値を取ると小さくなります
- 評価では、両方を分けて報告してください（平均のずれ、ずれの SD、相関）

**フレームレートの目安**：接地時間は約0.25秒なので、1コマの長さが誤差の下限になります。30fps で33ミリ秒、60fps で17ミリ秒、120fps で8ミリ秒。**目標の0.010秒には120fps以上が必要**です。

## 5. 精度を確かめるのに使える公開データ

| データ | 中身 | ライセンス | 使い方 |
|---|---|---|---|
| **Synchronized Dual-System Marker-based and Markerless Motion Capture Dataset**（Zenodo 19720803） | 男子大学生21名。トレッドミルの歩行・時速8kmなど7種目を、マーカー式モーションキャプチャ（120Hz）とスマホ2台（30fps、正面と側方）で同時に記録。**スマホ動画から YOLOv8 で出した関節の座標（CSV）と、マーカーの C3D**。動画そのものは含まれない | CC BY 4.0 | 座標から上の値を計算し、マーカーから計算した値と比べる（系統誤差・偶然誤差の見積もり）。取得済み：`data/dual_system_markerless_2026/archives/`（座標と参加者情報。マーカーの C3D 654MB は未取得） |
| **Fukuchi 2017**（取得済み） | ランナー39名、トレッドミル、マーカー150Hz、床反力300Hz | CC BY 4.0 | マーカーを30・60・120fps に間引いて、接地・離地の検出と接地時間の誤差がフレームレートでどう変わるかを見る（床反力が接地の正解） |

## 6. 気をつけること

1. **姿勢推定の「股関節」の点は、研究データの股関節の位置と違います**（MediaPipe や COCO の hip は、骨盤の外側寄り）。`HADD` と `CPD` に系統誤差が出やすいので、正解データでずれを確認してください
2. **側方の動画では、奥側の脚が隠れて推定が不安定**になります。手前の脚の値を優先し、奥側は信頼度が低いと `quality` に記録してください
3. **カメラが真後ろ・真横からずれる**と、角度が変わります（特に `HADD`、`KA`、`CPD`）。ずれの目安（例：左右の肩の点の見かけの幅）を `quality` に入れると後で判断しやすくなります
4. **角度の向き（符号）**：上の定義と逆にならないように、テスト用の動画で「膝を内側に入れて走る」「骨盤を大きく落として走る」を撮り、符号を確認すると確実です
5. **学習の方法について**：角度や接地のタイミングを正確にするには、正解データ（マーカーや床反力）と比べる**教師あり学習**（姿勢推定モデルの追加学習や、推定した座標から値への補正モデル）が一般的です。強化学習を使う場合は、何を報酬にするかを先に決めてください

## 7. ブラウザで動画を解析する場合（公開版の Web サイト）

公開版では、ユーザーがブラウザに動画を読み込み、**端末の中だけで**値を出します（動画はどこにも送信しない）。値の定義・向き・目標の誤差は 1〜6 と同じです。この章では、**ブラウザで動かすための追加の条件**を決めます。

### 7-1. 渡してほしいもの：JavaScript の関数1つ

```js
// 戻り値は 2 の measures.json と同じ形。測れなかった値は null
const measures = await extractMeasures(
  { rear: File, side: File },                                   // ユーザーが選んだ動画（どちらか片方だけでも動くように）
  { speed_kmh: 10, height_cm: 172, mass_kg: 64, sex: "M" },     // 画面で入力した値
  { onProgress: (p, message) => {}, fps: null }                 // 進み具合（0〜1）。fps が分からないときにユーザーが選んだ値
);
```

- 画面側では、この結果を `StrideModel.evaluate(measures, APP_DATA)`（`analysis/step6_app/app/model.js`）に渡すだけで、今の画面がそのまま動きます
- 撮り直しが必要なとき（全身が映っていない、歩数が足りない など）は、例外ではなく `quality.notes` に理由を入れて返してください。画面で撮り直しを促します
- `measures.json` に次の2つを追加してください（結果の比較と、提供されたデータの管理に使います）
  - `video.fps_source`：`video.fps_rear`・`video.fps_side`（実際に使った fps）の決め方。`"metadata"`＝ファイルの情報から読んだ、`"user"`＝ユーザーが選んだ
  - `model`：`{"pose": "姿勢推定モデルの名前とバージョン", "extractor": "このコードのバージョン"}`
  - `video.frontal_view`：`video.rear` の動画を撮った向き。`"rear"`＝後方から、`"front"`＝前方から（前方の動画は後方の定義に合わせて左右を読み替える。いまの計算では `KA` の向きだけが変わる）
- Node.js かヘッドレスブラウザでも動かせる形にしてください（自動テストに使います）

### 7-2. モデルは「ブラウザで動く形式」で作る

Python（PyTorch など）でしか動かないモデルは、ブラウザでは使えません。処理を3段に分けると作りやすくなります。

| 段 | 中身 | ブラウザでの形 |
|---|---|---|
| 1. 姿勢推定 | 各コマの関節の位置 | 学習済みモデルを使う。例：MediaPipe Pose Landmarker の JavaScript 版（`@mediapipe/tasks-vision`、Apache 2.0） |
| 2. 値の計算 | 接地・離地の検出、立脚中期、角度、歩ごとの中央値 | 普通の JavaScript |
| 3. 補正のモデル | 1・2 の値を正解に近づける（強化学習などで作る部分） | **ONNX**（ONNX Runtime Web で動かす、MIT）か **TensorFlow.js**（Apache 2.0）で書き出す。回帰の係数のような小さいものは JSON でよい |

- **モデルファイルの合計は 30MB 以下**を目安に（スマホの通信で読み込むため）
- **ライセンス**：公開の Web サイトで配るので、Apache 2.0・MIT などのモデルを使ってください。**YOLOv8（Ultralytics）は AGPL-3.0** で、Web で公開するとソースの公開義務などが生じるため避けてください

### 7-3. 学習と本番で、同じ姿勢推定モデルを使う（重要）

- 補正のモデルは、姿勢推定モデルのクセ（例：hip の点が外側に出る）を学習します。**学習に使った姿勢推定モデルと、ブラウザで使う姿勢推定モデルは同じもの・同じ設定**にしてください。YOLOv8 の座標で学習して MediaPipe で動かす、は不可
- 5 の Zenodo 19720803 には**動画そのものが入っていない**（YOLOv8 の座標だけ）ため、ブラウザで使うモデルの最初から最後までの検証には使えません。検証には、**チームで撮った動画と正解の値**（Kinovea などでの手作業の計測、可能ならマーカーや床反力）を使ってください
- Python 版の MediaPipe と JavaScript 版の MediaPipe でも、関節の位置がわずかに違うことがあります。学習を Python で行う場合は、同じ動画で両者の値を比べ、差が目標の誤差より十分小さいことを確認してください

### 7-4. ブラウザならではの注意

| 項目 | 注意 | 対応の例 |
|---|---|---|
| fps | ブラウザは動画の fps を直接教えてくれない。接地時間の精度に直結する | ファイルの情報から読む（mp4box.js、BSD-3）。読めなければユーザーに選んでもらう |
| スロー動画 | iPhone・Android のスロー動画（120/240fps）は、ファイルによって再生速度と実際の fps の扱いが違う | **実機で撮ったファイルで**、1秒あたりのコマ数と動画の長さが正しく取れるか確認する |
| コマの取り出し | 普通に再生するとコマが飛ぶ | `requestVideoFrameCallback` か WebCodecs（`VideoDecoder`）で、全部のコマを順に取り出す。対応していないブラウザもあるので、主なブラウザ（iOS Safari、Android Chrome、PC の Chrome）で確認する |
| 動画の形式 | iPhone の HEVC（.mov）は、Android や Windows の Chrome で再生できないことがある | 対応する形式を決めて画面に書く。読めないときは分かるエラーを返す |
| 処理時間 | 長いと途中でやめられる | Web Worker（裏側の処理）で動かして画面を固めない。**目標：10秒の動画2本を、数年前の普通のスマホで2分以内** |
| メモリ | スマホは全部のコマを持つと落ちる | コマごとに関節の位置だけ残して、画像はすぐ捨てる |
| 送信しない | 動画と顔は端末の外に出さない | 外部への通信はモデルファイルの読み込みだけにする |

### 7-5. 受け入れの確認

次のセットを一緒に渡してください。こちらで、画面に組み込む前に確認します。

1. **テスト用の動画**：5本以上（後方・側方）。条件の違うものを含める（踵接地／踵以外、iPhone／Android、60fps／120fps 以上）
2. **期待値**：各動画の正解の値（手作業の計測など）と、あなたの実装が出した `measures.json`
3. **誤差の表**：値ごとに、正解との平均のずれ・ずれの SD・相関（4 の優先1・2の値は必須）。4 の「許容できる誤差」に入っているか
4. **動作の記録**：試した端末・ブラウザと、それぞれの処理時間

こちらの確認：
- ブラウザ版の出力が、渡してもらった `measures.json` と一致するか（同じ動画・同じ端末で）
- 画面の計算（`StrideModel.evaluate`）に入れて、タイプ・予測・負担が表示されるか、値の範囲外の印が出すぎないか
